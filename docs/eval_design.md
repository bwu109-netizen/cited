# 第 2 阶段评估设计（eval design）v0.1

只写设计，不跑评估。目的：在开发集以外的约 60 份财报上，比较两种做法的准确率、编造率、错误能否被自动发现、成本和稳定性：

- **流水线**：页面定位 → 模型抽取 → 代码换算 → 核验
- **直接问**：把全文给模型，像聊天一样直接问

模型分便宜和最强两档，与两种做法交叉，共四格。

口径以 `docs/metrics_spec.md` v0.3 为准。

## 1. 评估集（60 份，三地各 20 份，不含开发集 9 家）

### 1.1 选择原则

- **报告范围**：全部是 2026 年发布的报告。多数是 2026 年中报或二季报，另加少量 2025 年报（文档最长）、2026 年一季报（文档最短）和非自然年财年（MSFT 6 月、NVDA 1 月、联想 3 月、新鸿基 6 月），用来考验期间判定。
- **上一期**：每家都已确认能拿到上一期报告（第 3 阶段跨期追踪要用）。“上一期”指按时间顺序紧挨着的前一份定期报告：
  - 中报 → 一季报；没有季报的港股公司 → 上一年年报。
  - 一季报 → 上一年年报。
  - 年报 → 三季报；没有三季报的 → 中报。
  - 只交 20-F 的中概股 → 上一年 20-F。
- **核对方式**：下表不是凭印象写的。`scripts/eval_candidates.py` 对每家都实际下载并解析了目标报告，自动判定模板，识别单位和币种，从结构化数据读取盈亏，并解析出上一期报告是哪一份（只解析，不下载）。原始结果在 `data/output/eval_candidates.json`。
- **人工核对过的格子**：标“原文”的格子是我读原文确认的，例如联想的盈亏、渣打的币种。港股的盈亏来自东财，东财可能换算过币种，但符号可靠。不过联想“报告口径亏损、经调整口径盈利”这种情况，必须以报告口径为准。

## 2. 标准答案

### 2.1 评分条目（answer key 的“行”）

每份报告的评分条目 = 该报告模板的核心字段 × 应有期间。“应有期间”和流水线的 `expected_pairs` 规则相同：

| 模板 | 字段 |
|---|---|
| 通用 | 营业收入、归母净利润、基本 EPS、经营现金流、毛利（报表有毛利行，或能由营业成本推导时） |
| 银行 | 营业收入（扣信贷损失前）、归母、EPS、经营现金流、净利息收入、拨备前利润 |
| 保险 | 营业收入、归母、EPS、经营现金流；保险服务收入、保险服务业绩（新准则下有披露时） |

- **期间**：
  - 累计期间（H / YTD / FY / Q1）必有。
  - 利润表本身有单季列时，加上营收、归母、EPS 的单季（Q）。
- **不评分**：子字段（普通股归母、每 ADS EPS、股数）和行业特色指标。行业指标没有标准答案，只单独统计“⚠️ 只找到原文”的比例和人工抽查结果。
- **规模估计**：按候选清单的模板和期间算，约 60 × 7 ≈ **420 条**。

### 2.2 来源

| 市场 | 自动标准答案 | 自动答案缺的字段 | 怎么补 |
|---|---|---|---|
| 美股 | SEC companyfacts（XBRL），按 accession + 期末日 + 期间长度匹配 | 拨备前利润（无标准标签）、推导毛利（无 GrossProfit 标签的公司）、保险服务收入/业绩；个别公司缺 `NetIncomeLoss`（已用 ProfitLoss − NCI 推导，见 §1 的坑） | 进人工核对表 |
| A 股 | AKShare 东财报表（累计）；单季用 `stock_profit_sheet_by_quarterly_em` | 拨备前利润、保险服务收入/业绩 | 进人工核对表 |
| 港股 | **全部人工**（按你的要求）。东财港股数据只作为候选值之一出现在核对表里，不作答案，并按 EPS 探针标记“疑似已换算币种” | — | 人工核对表 |

另外有两种情况要进人工核对表的“争议行”，由你裁决：

- **四格一致，但与自动答案不同**：四格里有 ≥ 2 格给出相同的值，且这个值和自动答案（XBRL/AKShare）不一致。自动答案不一定对，第 1 阶段就见过东财口径不同的情况。
- **自动答案按 spec 口径明显不对**：例如某 XBRL revenue 标签含了不该含的项目。

### 2.3 港股人工核对表（设计）

**形式**：一个本地 HTML 文件（`data/review/hk_answer_key.html`），离线可用，进度存浏览器 localStorage，可以随时导出 CSV/JSON。如果你更愿意在网页上做，也可以发布成私有 Artifact，结果存进 Artifact 的数据库，我可以直接读取，不用传文件。

**每一行 = 一个评分条目**：

| 列 | 内容 |
|---|---|
| 公司 / 报告 | 名称、代码、文件名，链接到 PDF 对应页（`…pdf#page=N`） |
| 字段 + 期间 | 例如“营业收入 · H（2026-01-01~06-30）”。悬停显示 spec 口径原文（如“银行：扣预期信贷损失前”） |
| 候选值 | 1–4 个，来自四格首轮结果和东财（去重）。**不标来源**，按数值排序，避免你偏向某个方法。每个候选同时显示原文写法和换算后的值，例如 `401,243 人民幣百萬元 → 401,243,000,000 CNY` |

**快捷键**：`j`/`k` 上下行，数字键选择，`Enter` 下一条。

**排序**：同一份报告的行放在一起（只需打开一次 PDF），每份报告内先放候选一致的行（快速确认），再放有分歧的行。

## 3. “直接问”对照组

### 3.1 做法

- **输入**：与流水线解析后的全文完全相同（同一份 NFKC 文本，按页加 `[PAGE n]` 标记），不做页面定位、不删页。用同一份文本，是为了让两组的差别只来自“方法”，不来自 PDF 解析器的差别。
- **问法**：模拟研究员在聊天里提问，一次问完。指标清单和口径说明与流水线完全一样（同一份 `FIELD_DEFS`），这样差别不来自“模型是否知道口径”。示例：

  > 这是 腾讯控股 2026 年中期业绩公告全文。请告诉我以下指标（2026 年上半年；如果有单季也给出单季）：营业收入（收入总额行，含“其他”分部）、归母净利润、基本每股收益、毛利、经营活动现金流量净额。

- **不加的东西**：不要求 JSON，不要求照抄原文，不要求页码和引用，不做代码换算，不做核验，不补问。模型怎么回答就怎么收。
- **参数**：temperature 0（模型支持时），推理强度用各服务商的默认值，与流水线那一格保持一致。

### 3.2 超出上下文怎么办

**先看数据**：

- 四个候选模型（deepseek-flash、Claude Fable 5.1 / Opus 5.5、Gemini 3.1 Pro）的上下文窗口都是 **1M tokens**。数据来源：DeepSeek `/models` 接口、Gemini models 接口、Anthropic 模型页，均为 2026-10-06 查询。
- 候选 60 份全文的规模见 §4（按实测的 tokens/字符比例估算）。最大的一份约 39 万（BIDU 20-F，按 DeepSeek 分词器） tokens；换成 Claude 的新分词器约 +30%，仍远低于 1M。
- **结论：按目前的清单，不会出现超窗。**

**万一超窗的预案**（换公司或换模型时可能遇到）：

1. **首选：按页从前往后放满，截断尾部**，并在提问里告诉模型“文档被截断，只含第 1–N 页”。该份报告标记为“截断”，最终指标同时报告“含截断”和“不含截断”两个版本。
   - 理由：这最接近一个普通用户在聊天里粘贴超长文件的结果。
   - 刻意不做任何“智能”挑页：挑页就是页面定位，对照组会变成半个流水线，比较就失去意义。
   - 缺点：美股 20-F 的财务报表在文末（F 页），截尾会让直接问吃亏。所以截断件必须单独报告，不能混进总数。
2. **不选：分块提问再汇总（map-reduce）**。这本身就是一种编排流水线，会把“直接问”变成“另一种流水线”。
3. **不选：换用检索（RAG）**。理由同上。

### 3.3 自由文本回答怎么变成可评分的数字

分两步，全部在评分侧做，不算进“直接问”的成本：

1. **解析（便宜模型，deepseek-flash）**
   - 把回答文本交给解析器，要求它对每个 (字段, 期间) 只从回答里逐字抄出数字和单位词（如“1,781.81 亿元”“$57.3 billion”“约 4.67 亿元的亏损”），以及正负号线索（“亏损”“净流出”），输出 JSON。
   - 回答没提到的填 null；回答给了多个值或区间的，标 `ambiguous`。
   - 解析器**不允许**看财报原文，只看回答文本。
2. **代码核验与换算**
   - **防解析器编造**：解析出的每个数字串必须原样出现在回答文本里，与核验层 C2 的规则相同；不出现的进人工抽查队列。
   - **单位换算**：用 `units.py` 换算（补充“亿/万亿/billion/trillion”等口语单位）。“亏损/净流出/(x)”转为负数。
   - **精度**：按回答显示的精度确定误差容忍度（例如“1,781.81 亿”精确到 0.01 亿）。
3. **抽查**：随机抽 10% 的解析结果人工看一遍，报告解析器的错误率。若超过 2%，改用人工解析该格。

“直接问”被判错的条目，会在结果里附上回答原文片段，方便复核“是解析错了还是模型答错了”。

## 5. 稳定性

- **子集**：15 份，每个市场 5 份，每个市场里至少 1 家银行、1 家保险、1 份年报或长文档、1 家亏损公司。在四格首轮跑完之前就把子集固定下来（写死在配置里），避免看结果挑子集。
- **重复次数**：每格对子集再跑 2 次，每份共 3 次。重复时绕过本地缓存：缓存键加上 run_id，保证真的重新调用模型。服务商端的提示缓存只影响价格，不影响输出。
- **报告的数据**：

  | 指标 | 算法 |
  |---|---|
  | 条目一致率 | 3 次结果都相同的条目数 / 子集条目总数。“相同”指 3 个值两两在误差容忍度内；3 次都缺失也算相同 |
  | 准确率波动 | 每次运行算一个子集准确率，报告均值、最小值、最大值（即极差） |
  | 状态翻转率（仅流水线） | 3 次运行中核验状态（✅ / ⚠️ / ❌）不完全一致的条目占比 |
  | 漏抽波动（仅流水线） | 3 次中“漏抽”条目数的极差。第 1 阶段见过同一份报告某一轮漏抽单季的情况 |

## 6. 最终指标与算法

记号：

- **S**：全部评分条目，去掉人工标“原文没有/不适用”的。
- **答对**：对条目 *i*，预测值 *p*、标准答案 *t*，满足以下两条才算答对。
  1. 误差在显示精度内：|p − t| ≤ max(½ × p 的末位单位, ½ × t 的末位单位)
  2. 误差不超过 0.1%：|p − t| ≤ 0.1% × |t|

  第 2 条的作用是防止“约 1800 亿”这种粗略回答因为精度粗而算对。EPS 同样适用（2.98 要求 ±0.003）。
- **未作答**（缺失、null、ambiguous）一律算错。

| 指标 | 定义 | 说明 |
|---|---|---|
| **准确率** | 答对的条目数 / \|S\| | 按市场、模板、字段、期间类型分组报告。置信区间用以报告为单位的 bootstrap（1,000 次）估计 95% CI，因为同一份报告内的条目不独立 |
| **数字编造率** | 编造条目数 / 有作答的条目数 | **编造** = 答错，且预测值在全文中找不到对应数字（把原文所有数字按 1、10³、10⁴、10⁶、10⁸、10⁹ 缩放，忽略正负号，在 p 的显示精度内都对不上）。答对的不算编造，哪怕是模型自己算出来的（例如直接问时用营收减成本算出毛利） |
| **错误被自动标出的比例**（仅流水线） | 答错且状态为 ❌ 的条目数 / 答错的条目总数（含漏抽） | 同时报告：**误报率** = ❌ 中其实答对的占比；**静默错误率** = 状态为 ✅/⚠️ 但答错的条目数 / \|S\|。直接问没有核验层，此项记为 0 / 不适用 |
| ↳ 去循环版本 | 同上，但核验时**不用 C4**（只用 C1–C3 和合理性检查） | **必须报告**：美股和 A 股的 C4 用的就是作为标准答案的 XBRL/AKShare，直接算会自证循环、虚高。港股的标准答案是人工核对的，不存在循环 |
| **每份成本** | 产生一份答案的全部模型调用费用 / 报告数 | 流水线 = 抽取 + 补问；直接问 = 一次提问。直接问的解析调用单列为“评估开销”，不计入。按调用时刻的官方价格计算（DeepSeek 区分峰谷），不用本地缓存，服务商提示缓存命中按实际价格计。同时报告中位数、最大值、tokens 和耗时 |
| **稳定性** | 见 §5 | |

**主表格式**：

- 行 = 四格。
- 列 = 准确率（95% CI）、数字编造率、错误被标出比例（含 C4 / 去 C4）、静默错误率、每份成本、条目一致率。
- 另附分市场、分模板的明细表，以及全部错误条目的清单（附原因分类）。

## 7. 规矩：冻结与留痕

### 7.1 冻结

在**第一次**用评估集跑任何一格之前，冻结以下内容，并在 `eval/FROZEN.md` 里记录冻结时的 git commit 号：

- 评估集名单（含目标期间、上一期）和稳定性子集
- 全部提示词：流水线的抽取和补问提示词、直接问的提问模板、直接问回答的解析提示词
- 核验规则（C1–C4）、合理性检查（§7.3）、单位和币种解析、期间判定
- 评分规则（§6 的“答对”定义、编造定义）
- 模型 ID 和参数（temperature、推理强度、max_tokens）

冻结后，评估脚本启动时检查当前 commit 与冻结 commit 之间，上述文件有没有改动；有改动就拒绝运行，除非显式标记为“规则修订后重跑”。

### 7.2 跑完以后改规则

允许改，但必须同时做到下面三条：

1. 报告里列出每一处修改：改了什么（附 diff 或 commit）、为什么改、由哪些条目触发。
2. **同时报告改之前和改之后的结果**：主表的每个指标都给出两列（冻结版 / 修订版）。修订版用同一批模型输出重新核验和评分；如果改的是提示词，则重新调用模型，并注明这部分成本。
3. **不允许只报告修改后的结果。** 冻结版结果始终是主结果。修订版只能作为补充，并注明“规则在看过评估结果后修改”。

这与第 1 阶段的做法一致：发现规则误报后修正，并在 `phase1_review_notes.md` 里保留首轮误判。

## 8. 执行顺序（第 2 阶段开工后）

1. 固定评估集和稳定性子集，写入 `eval/config.json`；按 §7.1 冻结并记录 commit 号。
2. 实现直接问的提问和解析，以及评分器；先在开发集 9 家上试跑，验证解析器和评分器。
3. 四格首轮：60 份 × 4 格。
4. 生成核对表，你核对港股和争议行（约 2 小时）。
5. 稳定性：15 份 × 4 格 × 2 次。
6. 出结果：`docs/eval_results.md`。

## 9. 需要你决定的

1. **最强模型选哪个**（见 §4.1）。我的建议是 Claude Fable 5.1，先花约 50 美元在开发集上和 GPT-6-Astra、Gemini 3.1 Pro 各试一轮再定。需要你在 `.env` 里加 `ANTHROPIC_API_KEY`；如果试跑，还要加 `OPENAI_API_KEY`。现有的 Gemini key 可以直接用。
2. **最强模型的推理强度**：用各家默认值（Fable 5.1 默认 high），还是统一设为 low 来省钱？默认值更接近“最强”的本意，但输出 token 会多 2–3 倍。
3. **直接问的输入形式**：用流水线的解析文本（我的建议，两组输入一致），还是让 Claude/Gemini 直接读 PDF（更像真实聊天，但 DeepSeek 不支持 PDF，四格就不对称了）？
4. **港股核对表形式**：本地 HTML 文件（默认），还是发布成私有 Artifact（结果自动回到我这边）？
5. **答对的门槛**：误差 ≤ 0.1% 且在显示精度内（§6）。这个门槛对 EPS 和“约 X 亿”这类回答是否合适？
6. **评估集里的期间组合**：多数是 2026 年中报/二季报，另有少量 2025 年报、2026 一季报和非自然年财年。是否需要更多年报（年报最长、最难）？
