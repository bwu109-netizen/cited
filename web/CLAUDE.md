# Coding rules for the web directory (apply to web/ only)

> Source: Ponytail (https://github.com/DietrichGebert/ponytail, by Dietrich Gebert, MIT licence), a summary of the rules in `skills/ponytail/SKILL.md` v4.13.0, rewritten in our own words.
> No plugin installed, no Node, no hooks enabled, and no status-line badge (decided 2026-10-06).

## 0. Hard constraints of this project (take precedence over the style rules below)

- **Do not change core code**: `earnings_agent/`, `eval/` and `tests/` must not be changed; `.claude/settings.local.json` has deny rules. New code the site needs (including the Verify-page parser) goes under `web/`, and only imports the core modules. When core code really has to change, ask the user first; after they agree, they lift the deny rule temporarily.
- **Honesty**:
  - Evaluation numbers on the site come only from `docs/eval_results.md`.
  - No marketing lines generated by Stitch.
  - Never write "more accurate than asking AI directly", "zero silent errors", "every error is flagged" or "verified correct".
  - ✅ is labelled "passed checks" (通过核验), never "correct".

## 1. First ask "should this be written at all"; go down the list and stop at the first option that works

1. Is the feature really needed? Skip anything that is only "maybe useful later", and say in one line what was skipped.
2. Does the repo already have it? Look for existing functions and patterns first (`earnings_agent/` has extraction, verification, units and periods); reuse rather than rewrite.
3. Can the standard library do it? Use the standard library.
4. Can the platform do it natively? If Streamlit's built-in components, native HTML controls or CSS solve it, do not add JS or a new library.
5. Can an installed dependency do it? Then use it; do not add a dependency for a few lines of code.
6. Does it fit in one line? Then one line.
7. Only if none of the above works, write the least code that works.

Understand the problem and the code involved before going down the list. The list shortens the solution, not the reading.

## 2. Rules

- No abstractions nobody asked for: no interface with a single implementation, no factory that makes one thing, no configuration that never changes.
- No scaffolding "for later".
- Deleting code beats adding code; plain beats clever.
- Fewer files and shorter diffs are better, provided the change is in the right place.
- Fix bugs at the root: find all callers of the function being changed and fix it once where they all pass.
- A deliberate simplification with a known limit gets a `# ponytail:` comment stating the limit and how to upgrade later, e.g. `# ponytail: global lock; switch to per-job locks if throughput becomes a problem`.
- Logic with branches, loops, parsing or numbers gets at least one runnable check: a small test inside `web/` or a `__main__` self-check. No test framework.

## 3. Where not to cut corners

- Input validation at trust boundaries: uploaded PDFs, pasted AI answers, the user's key.
- Error handling that prevents data loss or leaks: keys are never written to disk or logs.
- Security and basic accessibility (readable contrast, keyboard use, mobile use).
- What the user explicitly asks for: do it, without arguing again and again.

## 4. Output

Code first, then at most three lines on what was skipped and when it should be added. Explanations the user asks for (reports, step-by-step notes) are written in full as usual.
